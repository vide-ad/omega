## 1. What Omega is

A single-user hypertrophy and endurance training log, replacing Strong. Four things Strong does not do:
context-aware progression (a rolling baseline of *qualifying* sessions, so a bad week cannot trigger a
false regression), per-muscle weekly volume accounting with fractional set credits, injury-constrained
prescription, and a REST API an LLM coach reads and writes.

## 3. The spec was generated by a chat and had 32 internal contradictions

David had his gym Claude generate the build spec. I had it audited and found 32 issues, three of them
blockers. They are all resolved in `docs/ENGINE-RULES.md`, which now supersedes the spec where they
disagree, with a table of every deliberate deviation.

The worst: §5.2 makes a constrained exercise "compromised", and §5.3 says compromised exercises never
qualify for progression. So every curl under David's radial-nerve constraint would read "set a starting
load" forever — contradicting §3.2 and §9.4, which both assume constrained lifts *are* prescribed, just
capped. **I reversed it:** constrained exercises qualify normally, and the constraint is applied as a
clamp after the load decision.

Other reversals worth your eye:
- **Soreness moved from session level to exercise level.** As written, sore biceps invalidated squat
  progression for the whole session. Now soreness only compromises exercises training that muscle.
- **Volume weeks anchored to the mesocycle start, not ISO weeks.** The training microcycle is Sat/Sun/Wed,
  which straddles two ISO weeks, so the dashboard would never line up with the block's ramp.
- **Null-RIR working sets count for volume** (§5.1) rather than being excluded (§4). The two sections
  contradicted each other outright.

**Is "the rulebook supersedes the spec" the right posture?** It is what let me ship, but it means a
document I wrote overrides a document David commissioned. Tell me if that should have gone to him
decision by decision instead.

## 4. Decisions since, in rough order of consequence

**The RIR effort test — a schema change, and the one I would most like challenged.**
David's UI/UX agent found that RIR was pre-filled at target and styled like a chosen value, so tapping
Log recorded an assumption as an observation. I verified against the built engine, target RIR 3, all
sets at the top of the range:

| What the lifter did | Reason | Prescription |
|---|---|---|
| Never touched the chip (pre-filled 3) | `progress_load` | 45 kg |
| Reported 2 — harder than asked | `consolidate` | 42.5 kg |
| Reported 4 — easier than asked | `progress_load` | 45 kg |
| No RIR at all | `first_time` | 42.5 kg |

An untouched default was indistinguishable from a positive report that the set was easy, and *more*
dangerous than recording nothing. Mean RIR is the single input the whole engine turns on. My decision:
add `SetLog.rir_observed`, and `progress_load` now requires observed effort. Assumed RIR still counts for
volume, qualification and rep progression.

The tension: this deliberately contradicts spec §7 ("pre-filled with the target"), and it means a lifter
who will not spend one tap never gets load progression. I think that is the right contract. It is
arguable.

**Flutter is the client; the PWA is a stopgap.** David's call, recorded in `docs/CLIENT-DECISION.md`.
The server side is untouched — the engine runs server-side and `POST /workouts` returns prescriptions
already computed, so the client renders rather than calculates and never needs the engine in Dart.
Plan is to deploy the PWA now and train on it while Flutter is built page by page against an API that
already has real data in it. Cut over when ready, same database, no migration.

**Readiness demoted.** David finds it unnecessary. Kept in schema and API, dropped from the nav, with the
"today was rough" toggle moved onto the session screen. Stated consequence: without a readiness log the
only session-level compromise triggers left are the deload week and that toggle, so a genuinely bad day
is read as real and two in a row drop the load 10%. Pain flags are unaffected, so injury protection
survives and fatigue protection does not.

**Coach writes still mutate directly.** Spec §6.2 wants `pending_review` proposals the user approves.
Deferred. Until it ships, the coach gets a read-only token. Flagging because it is the one deferral that
could bite: a coach token with write access could silently rewrite templates or volume targets.

## 5. What I got wrong

- **I built the whole UI at once.** 3,400 lines, now being rewritten in Flutter. David wanted page by page
  and was right; the interface is the product for a training log. Building the API and engine fast was
  correct — they are proven and give the Flutter lane a real backend — but I should have stopped there.
- **I asserted a colour encoding without measuring it.** My "brass means the engine is speaking" idea was
  sound and I then picked a brass sitting ΔE00 4.5 from the amber I used for three other meanings. The
  design agent measured it; I had eyeballed it.
- **I told David "agent-bridge" did not exist as a definite tool.** I had searched public repositories.
  It is his own `D:\Coding\bridge.py`. I answered the question I could search rather than the one asked.

## 6. Lanes — your ruling, please

The team changed under me. `docs/LANES.md` still describes three lanes (web / api / core) sized for a
React app and is now wrong. Current shape: **chalk** as PM, one **lead coder/UX agent** on Flutter (not
cass, who stays on North), and no named owner for backend work.

Outstanding backend work is small and finite: the RIR effort test (~an hour, fully specified),
`DELETE /workouts/:id/exercises/:weid` (missing), and proposals (medium, deferrable).

- **A — one coder does everything.** No coordination overhead, no directory-ownership rules, no worktrees.
  Serialises the backend behind Flutter screens.
- **B — lead coder on Flutter, a second agent on API and engine.** Parallel, but needs the ownership
  boundaries that Omega's docs already describe, for about a day of backend work.

**My recommendation is A, with the RIR fix as the coder's very first task, before any Flutter screen.**
It is an hour, it is specified, and it protects data that starts accumulating the moment the PWA is
deployed. Two agents coordinating over one day of backend work looks like a bad trade for a single-user
app. But you have run this team longer than I have — if the August clobbering makes you want hard lane
separation regardless, say so and I will write it that way.

## 7. Open, needing David

- **A hostname.** The only thing between him and logging real sessions. Needed for either client, since a
  native app still has to reach the API over HTTPS.
- **Seed volume tuning.** As seeded, `set_delta` 0,1,2,3,3 on every priority slot puts quads at ~32 weekly
  sets against a 15–20 target by week 4. The dashboard will read "over" for a whole block. Audit suggested
  priority on only the first quad slot per day and a 0,1,1,2,2 ramp.
- **Two seed oddities:** "Preacher Curl" and "Machine Curl" look like the same machine seeded twice, and
  the Bayesian cable curl is a standing exercise while the physio note says seated only.
